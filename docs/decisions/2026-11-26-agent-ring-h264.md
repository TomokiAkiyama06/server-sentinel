# Owner decision: Agent ring recording format and incident trigger (Issue #16)

Date: 2026-11-26
Decision by: repository owner
Recorded in: Issue #16, PR A (segment format core)

## Decisions

1. **Codec.** The `media-capture-agent` re-encodes each approved camera's
   MJPG frames to H.264 with OpenH264 (BSD-2-Clause, GStreamer `openh264enc`)
   on the capture host, and the disk ring stores those H.264 segments. The
   alternative of storing the camera's MJPG unchanged was declined in favour of
   a longer retention for the same capacity. As for the Main Server (D13,
   2026-11-08), x264 (GPL) is not used and NVENC is not used by the Agent.
   On a Debian/Ubuntu capture host the encoder comes from the distribution
   packages `gstreamer1.0-plugins-bad` and `libopenh264-7`; installing them
   on a production host is a separate, Owner-confirmed step (PR B).
2. **Container.** Every ring segment is one self-contained fragmented MP4
   (`ftyp`+`moov`+`moof`+`mdat`, one video track, no audio) written by the
   Agent's own standard-library writer, consistent with D13's own fMP4 writer
   decision for the Main Server. GStreamer only encodes (and, for validation,
   decodes) in child processes.
3. **Bitrate for 1280x720@30.** Encoder target 2 Mbps; the ring profile's hard
   per-segment bound uses 4 Mbps (`maximum_bitrate`) and the estimate uses
   2 Mbps (`expected_bitrate`). These are starting values to be re-measured on
   the real capture host; at 2 Mbps a 100 GiB ordinary ring holds about five
   days.
4. **Incident trigger (T0).** Every loss of an established authenticated
   session to the Main Server that the Agent's reconnect does not recover
   starts the 10 min pre-loss + 10 min post-loss protection, including a Main
   Server that stops or restarts on purpose. Only the Agent's own shutdown is
   excluded.
5. **Order of work.** PRs A–D first: segment format core (A), deviceless
   encoder child (B), recorder wiring with T0 and clock holdover (C), and an
   Owner-only local `ring_admin` command (D). The Main Server preserve
   command / heartbeat summary (E) and the dashboard view (F) follow.

## Defaults chosen with the plan (adjustable without a new decision)

10 s segments (300 pictures at 30 fps), GOP 60 pictures (2 s; it divides the
segment, so every segment starts with an IDR picture), a 64 KiB per-segment
container overhead bound, a 256 MiB ledger cap and a 15 min clock holdover.

## Evidence

- Synthetic-input tests: `agent/tests/test_recording_segment.py`.
- A disposable Ubuntu 24.04 container check (not the capture host): a
  `videotestsrc` pattern encoded by `openh264enc` 1.24.2 at 1280x720@30 with
  `gop-size=60`, split and validated by `h264_annexb`, written by `fmp4`,
  then read by `ffprobe` (H.264 Constrained Baseline, 300 frames, 10.000 s
  per segment) and decoded to the end by `qtdemux ! h264parse ! openh264dec`.
  Synthetic video only; no camera or real-person media.
- Not yet measured on real hardware: CPU load, real-scene bitrate and the
  segment byte bound, which PR B/C measure on the capture host.
